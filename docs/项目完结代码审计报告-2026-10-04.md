# 1. 项目整体评价

**整体 🟡 存在一定技术债；局部 🟠 存在明显复杂化（范围可控，不需要大范围重构）。**

理由（正反两面）：

**健康的部分（明确不值得动）**
1. 进程/职责分层是清楚的：内容脚本（检测/去字/排版/气泡）→ 本地服务（OCR + 翻译）
   → ollama（推理）。`server/app.py`（OCR+翻译，11436）与 `server/ollama_server.py`
   （引擎+模型，11437）边界干净，头部注释即契约。
2. 有真实的架构护栏：`scripts/check-extension-architecture.mjs`（先擦注释再匹配，避免注释误报）、
   `check-workspace-import-boundaries.mjs`（跨包边界 + 无环，baseline 为空）。
   全仓库**没有** `eslint-disable`/`@ts-ignore` 式的边界绕过（除 apps/web 一处与一条测试）。
3. 测试是有的且不少：175 个测试文件；服务端 27 条纯函数测试钉住的是真逻辑（切段、输入分流、
   置信度数学、强制卸载语义），不是只测常量。
4. 注释写的就是"为什么"（典型反面教材的反面）：踩过的坑、为什么不能改顺序，都留在代码旁。

**不健康的部分（本报告主体）**
1. 有 **4 处完整死子系统**仍在仓库里（HostThrottle / PageCacheManager / 窗口规划函数 /
   `mt:translation-cache` 整条磁盘缓存维护通道），其中一处（死消息通道）在运行时**不可达**。
2. **同一语义多个来源**：显示模式有 3 个持有者且判定需两处同时成立；后台还反向 import 内容脚本模块。
3. **首轮修根因之后留下旧壳**：这类残留是本项目技术债的主要形态（不是"屎上雕花"，是"改完没清场"）。
4. **文档与实现大面积不一致**，个别处会直接误导使用者（README 把模型控制面板写成 11436）。
5. 我自己在最近几轮引入的 3 处缺陷仍在树里（T4 坏、`_pad_token_id` 重复、置信度异常返回 1.0）——
   说明"改完立即验证覆盖面"这件事在流程上还缺一道闸。

# 2. 最重要的问题（按严重程度）

## P0-1 显示模式有三个来源，且"全局"语义靠巧合成立

**【位置】** `apps/extension/src/content/core/TranslatorCore.ts:284,291,305,324`；
`apps/extension/src/content/core/translation/imageTranslationController.ts:137-138,247`；
`apps/extension/src/content/core/reading/readingModeController.ts:54,209,293`

**【问题】** 三处各持一个显示模式状态：`TranslatorCore.displayMode`（全局）、
每图 `PhotoState.mode`（仍参与判定：`TranslatorCore.ts:305`
`this.displayMode === 'translated' && state.mode === 'translated'`、`:324`
`state.mode === 'translated' ? state.translatedUrl : state.originalUrl`）、
`readingModeController.globalTranslateMode`。写入点分散在 5 个地方。

**【原因】** 2026-10-04 拍板改成"全局显示模式"时，**新逻辑是盖在旧逻辑上的**：
全局 flag 加进来了，但每图 `mode` 没被降级为纯数据，仍在参与"该贴哪张图"的判定。
注释也写着"无全局开关的调用方（twitter 轮播）保持每图独立的旧语义"，于是两套并存。

**【影响】** "切一次所有页一起切"这个保证不来自代码结构，而来自"两处状态当前恰好一致"。
任何一处漏写（controller 里翻 `state.mode`、reading 里翻 `globalTranslateMode`），
就会出现"点了切换但某页没跟着变"。这是最容易产生隐藏 bug 的地方之一。

**【建议】** 全局显示模式**唯一**；`PhotoState.mode` 退化为"这一页是否已有译图"（或直接删掉，
用 `translatedUrl` 是否存在判断）；阅读模式复用同一个全局量而不是自建一份。
工作量小（三处读点），但必须同时改三处写点，改完加一条"任选两页切换后两页都变"的行为测试。

## P1-1 预取链条：三套推进机制 + 四个并存状态（公认最难改的区域）

**【位置】** `content/core/scheduler/prefetchChain.ts`（325 行）：`windowAnchorPage` 锚点、
`advanceToWindowEdge` 边缘推进、`notifyDispatchFailed` 失败自动补发；状态字段

**【建议】** 认账、不重构。只做两件低风险事：① 在文件头写一张"决策流程图"（哪条路径何时生效）；
② 给"当前页是否算入窗口"抽一个具名函数（现在散在布尔三元里）。**不建议合并三条机制**——
那属于重写，收益不确定而风险确定。

# 4. 可以简化的地方

1. **状态**：显示模式从 3 个来源收敛到 1 个（P0-1）；`PhotoState.mode` 降级为派生值。
2. **配置字段**：`normalizeProcessMode()`、`normalizeImageEngine()`、`normalizeGeminiAppAuthMode()`
   现在都是"无视入参、恒返回常量"的空壳（`shared/config.ts:263,268,272,276`）——
   它们只起"吃掉旧值"的作用。可保留函数但删除对应字段与 UI 残留（否则字段永远存在却无人读）。
3. **分支**：`server/translate.py` 的 `if len(chunks) == 1 and len(chunks[0]) == len(idxs)`
   第二个条件恒真（分块保序不丢元素），冗余。
4. **多余兜底**：`TranslatorCore.ts:353` 附近 `decode().then(go).catch(go)` +
   `setTimeout(go,500)` 三重兜底，可简化为"decode 或超时，二选一"。
5. **消息通道**：`mt:translation-cache`（磁盘，死）与 `mt:memory-cache`（内存，活）
   两套做同一件事——删前者的同时也就简化了弹窗的调用路径。
6. **模块耦合**：`background → content/core` 的纯函数上移（P1-2）。
7. **文件职责**：`content/index.ts` 拆出"预载开关 UI"（P1-4）。

**明确不值得简化**（避免为了优化而优化）：
- `router.ts` 的 `MessageOf/SuccessOf/PayloadOf` 类型体操 —— 换来编译期消息契约一致，删了更容易漂移。
- `packages/image-runtime`/`model-runtime` 的 interface 与 factory（`ModelRuntime` 有 browser/node
  两实现；`PipelineHostLifecycle` 有 Chromium/Firefox 两实现）—— 是真实多实现，**不是过度设计**。
- `vram.py` 的六层卸载函数、`ocr.py` 的批量→逐张多层回退 —— 每层都为真实故障加的，语义清晰，注释完整。
- `sourceGeometry.ts`、`ui/index.ts` 这类 barrel re-export；`app._health` 读 `ocr_mod._ocr`（为了不触发懒加载的有意取巧）。
- `launch_silent` 与 `nm_launcher` 各写一份静默启动 —— 诉求不同（NM 要协议透传）。

# 5. 架构问题（只列影响长期维护的）

1. **分层越界且护栏查不出**：`background` 相对导入 `content/core`（P1-2）。护栏只覆盖
   浏览器命名空间与跨包边界，**"同 app 内跨层"没有规则**。这是最容易被持续复制的一类。
2. **settings 有三个化身**：权威 settings（background/存储）↔ 内容脚本模块级副本
   （`prefetchToggleDepth`/`prefetchToggleOn`）↔ 执行器自己的 depth。
   链路上还有 `applyPrefetchConfig = null` 的异步赋值槽（`content/index.ts:108,174`）。
   根因是"内容脚本拿不到 settings"（架构限制），不是设计懒；但**每加一个设置项就可能再加一个槽位**。
   长期方向：内容脚本只保留"当前配置快照"一个对象，禁止散落模块级变量。
3. **三层消息转发**（content → background → offscreen）加上两条"读+写"配置通道
   （`mt:prefetch-config-sync` 与 `mt:prefetch-config`），已经出现过"两边互推死循环"的坑
   （代码注释记录了）。这不是当前故障，但属于结构性脆弱点。
4. **本地服务双进程 + 端口三处**：11434/11436/11437 在 TS 与 Python 各写一份，
   `server/config.py` 与 `server/service_control.py` 又各写一份。改端口要改 4-5 处。
5. **原项目扩展机制**：整体是**沿用了**上游机制的（站点适配器 `adapters/*`、readerEngines、
   provider 注册表、messages 契约），没有绕开重建。唯一"另起一套"的是
   `prefetchChain`+`showpageClient`（e-hentai 特有的翻页预取），但它确实是项目核心需求，
   上游没有对应能力。**这条算合理，不算问题。**

# 6. 维护风险（最容易出事的地方）

1. **`prefetchChain.ts` / `prefetchExecutor.ts`**：三条推进路径 + 四个状态字段 + 布尔决定窗口下界。
   任何"再修一次"都可能叠第四层。**改它之前先把决策流程画出来**。
2. **显示模式的三来源**：漏写一处写点 → "切换某页没跟着变"的偶发 bug，且不易复现。
3. **"必须保持同步"的隐性约束**：`imageTranslationController.ts:216` 注释明写
   "到这一行为止必须保持同步…一旦把 await 插到上面去，测试立刻红"。
   这是**测试反向约束实现细节**——重构这段代码的人几乎必然先踩一次。
4. **UI 层三个"隐形陷阱"**（本轮已各踩一次）：
   `styles.ts` 是模板字符串（注释里写反引号会截断模板）；
   运行中按钮不可点要先分清 disabled / `pointer-events` / 事件没接上；
   共享组件（`renderUi`）被截图 UI 复用，改共享行为要先确认另一调用方是否有对应能力。
5. **文档漂移**：本报告 §P1-3 那份清单就是"6 个月后接手人会被误导"的具体位置。
6. **测试的假安全感**：窗口规划两条测试测的是生产不用的函数（P0-3）；
   `ollama_server.py`（双服务架构的一半）、`service_control` 的优雅关停顺序、
   `ocr._conf_from_scores` 的对齐层 —— **都没有自动化测试**。
   "先卸模型再停引擎"这条拍板硬约束目前只靠注释保护。
7. **`binbContent` 的像素矩阵测试偶发失败**（单独复跑必过）——已知 flake，会周期性浪费排查时间。

# 8. 最终结论

**1）有没有明显的"屎上雕花"？**
没有大面积的。历史上有过一段"为观测一个 bug 而长出诊断装置"的时期（缺口原因分类、
末页截断分母、`advancing` 标志…），但那批已在 2026-10-04 用奥卡姆剃刀撤掉（净删 136 行），
代码里保留了说明性注释。**当前形态的主要问题是"改完没清场"（死代码 + 文档漂移），
不是"为改而改"**。

**2）有没有补丁叠补丁？**
有，但可枚举、且集中在两处：`prefetchChain`（锚点/边缘推进/失败补发三套 + 四状态）、
显示模式（全局 flag 盖在每图 mode 上）。两处都有完整注释交代来龙去脉。
**不是全项目性的叠补丁**，也没有"用 try/catch 掩盖设计问题"的普遍现象
（105 处 catch 里，绝大多数是合理降级；真正有害的只有 `_conf_from_scores → 1.0` 一处）。

**3）有没有明显过度设计？**
个别：`HostThrottle`、`PageCacheManager`、四个恒常量的 `normalize*`、死的
`mt:translation-cache` 通道。**其余抽象（arbiter/model-runtime/provider 注册表/消息契约）
都有真实多实现或测试替换价值，拆掉反而更糟。**

**4）有没有可以直接删除的一批代码？**
有，且证据充分：HostThrottle（+其测试）、PageCacheManager、窗口规划两函数、
`freezeScreenshotResultOverlayPosition`、`mt:translation-cache` 整链、
`ppl_geomean`/`STAGE_KEYS`/`TOKEN_KEYS`、`resolveAssetUrl`、`OLLAMA_PORT`、
三个死设置字段、未使用 CSS 类，以及 `probe/`、`run/` 的一次性诊断物与过期文档。
合计约 **600-800 行代码**（不含测试）与若干杂物。

**5）有没有应该重构的局部实现？**
三处，按序：
(a) **显示模式单一来源**（唯一我建议现在做的结构性重构）；
(b) **`buildPageCacheKey` 上移 + 架构护栏补规则**；
(c) **`test_server.py`/`ocr.py` 的清尾**（这是回归修复，不是重构）。
另有两处"值得但不急"：`localPipelineClient` 的 Port 会话去重、`screenshotController` 两函数合并。
**不建议动 `prefetchChain`**——重写风险大于收益。

**6）当前代码是否已经达到可以停止折腾的程度？**
**达到。** 除了上面 P0 的三项（坏掉的 E2E、重复定义与口径相反、会误导人的文档）必须收尾，
其余都属于"下次真的遇到问题时再动"。核心链路（翻页预取 → OCR → 翻译 → 贴图）
有测试、有遥测、有注释交代历史；继续加功能前先把 P0 清掉、把 P1-1 的显示模式收敛掉，
这个项目就处在**可持续维护**的状态——**不需要重写，也不需要为"最佳实践"再折腾一遍**。
