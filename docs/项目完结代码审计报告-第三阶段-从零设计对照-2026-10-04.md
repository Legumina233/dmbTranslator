# 1. 从零设计概要

如果今天从零做这个产品，我会做下面 10 个决定（D1-D10）。**注意：其中 7 个与现状一致。**

**D1 上下文与职责（与现状一致）**
`content`：站点交互 + 显示决策 + 用户操作；`background`：设置权威 + 任务编排 + 消息路由；
`offscreen`：ONNX 重活（检测/消字/排版）；`popup`：设置 UI；本地服务两个进程（OCR+翻译 / ollama 控制）。
→ 这是 MV3 与"显存互斥"共同逼出来的形状，没有更简单的选择。

**D2 页身份与缓存（与现状一致）**
`pageKey = ${gid}-${page}`，只从 pathname 派生；缓存键 = `pageKey + (ocr,llm,typeset)` 三个版本；
**内存优先、不落盘**（产品已决策）。人读不出来的 key 一律不做主键。

**D3 预取：一个"取数与翻译的单一队列"（与现状不同）**
一个 `GallerySession` 模块持有：`window = [current, current+depth]`、一个 `wanted: Set<key>`、
一个 `pump()`。取 JSON（链）与翻译（CPU/GPU 任务）是**同一队列的两种任务**，
派发顺序由一个规则决定：*"窗口内任何页，若其 JSON 缺失 → 先补 JSON；若有 JSON 无译图 → 交给翻译器"*。
窗口边缘的推进不写成"边沿推进函数"，而是让 `pump()` 每次重算 `wanted` ——
**补上缺口是重算的自然结果，不是需要额外维护的动作**。
（现状是 `prefetchChain`（JSON 链）+ `prefetchExecutor`（翻译队列）两个模块，
外加"到达页数据已在手就地返回"这个曾经的主路径 bug 与它的边缘推进补丁。）

**D4 显示：一个全局枚举 + 页级"有没有译图"（与现状不同）**
`displayMode: 'original' | 'translated'` 全局唯一；页级只存 `translatedUrl?`。
"这页该显示什么"= `displayMode === 'translated' && translatedUrl ? translated : original`。
**不存在页级 mode 字段**，也就不存在"两处状态要同时对上"的问题。

**D5 配置：单一来源 + 每任务快照（与现状一致，但内容脚本侧不许留副本）**
settings 权威在 background；每次任务把 `toPipelineConfig(settings)` **快照**随任务下发（现状就是这样，`translationConfiguration.ts:130`）。
内容脚本**只保留 UI 需要的只读快照**，其余设置一律不落模块级变量。

**D6 配置校验：一个 parser（与现状不同）**
`parsePipelineConfig(unknown): PipelineConfig | null` 只写一份；消息解析、任务校验、协议编解码**都调它**。
（现状：`image-pipeline/index.ts:390 validateConfig` 与 `protocol/index.ts:554 isValidPipelineConfig` 各写一份。）

**D7 取消：每任务一个 AbortSignal（与现状不同，但现状的额外层有职责）**
我会给每个任务一个 `signal` + `cancel(reason)`；trace 用一个小的上下文对象承载。
现状的 `arbiter`（begin/end/revoke + activity + 三阶段撤销）更厚，
但它同时承担 M1 五态 trace 与"同页只跑一条管线"的去重，**这两件事我确实需要** →
所以这是"实现方式不同、现状不亏"，不是该重构项。

**D8 服务层：端口/URL 单源 + 关停顺序是服务端不变量（与现状基本一致）**
两个服务共用一个 HTTP handler 基类（cors/send/passthrough）；
"关 ollama = 先卸全部模型 → 再停引擎 → 确认端口"写成服务端不变量 + 一条测试；
扩展只认一个 `localServiceClient` 作为端口/地址的唯一出处。

**D9 OCR：一个引擎（与现状不同）**
只保留服务端 manga-ocr，**显式失败、不自动回退**。
不会保留一个"默认不用、失败也不用"的第二实现（现状还留着 PaddleOCR ONNX + 76MB 资产）。

**D10 尽量复用上游机制（与现状一致）**
站点适配器、readerEngine 注册表、OCR provider 注册表、消息契约类型、image-pipeline 的
检测/气泡/消字/排版 —— 全部沿用，不自己另起一套。**唯一自建的是 e-hentai 预取链**，
因为上游没有这个能力（那是本项目要解决的核心问题）。

# 3. 当前实现中值得保留的部分（即使和从零设计不同）

1. **常驻画框（不改站点 `<img>` src，译图画在自己的浮层上）** —— 从零设计我未必能想到：
   站点重建图片 DOM 时不会被我们改动干扰，是踩出来的最优解。**绝对保留。**
2. **预取链"从在手 JSON 逐跳找缺口"的算法** —— 这是 imgkey 只能在前一页 JSON 里这一约束下的
   正确算法。现状把它拆成 chain/executor 两模块、加了边缘推进补丁，但它**能工作且被真机验证**；
   我的"单一队列 + 重算 wanted"在纸面更干净，但重写要重新面对软导航时序/去重/失败重发。
   **保留，不重写。**
3. **内存优先、不落盘的译图缓存 + `PhotoStateStore` 的 limit/protect** ——
   直接消灭了"磁盘与内存不一致 / 跨版本缓存失效"一整类 bug；`protect` 解决长页面淘汰在用译图。
   **保留。**
4. **失败语义**：OCR/翻译失败必须显式报错，绝不静默回退（"服务没开"不能被伪装成"质量变差"）；
   服务端 P0-B/P0-C（失败必抛、先落盘后响应）。**保留，这是项目的价值观。**
5. **Windows 进程陷阱的沉淀**：`CREATE_NEW_PROCESS_GROUP`/隐藏控制台/DETACHED、
   托盘版 `ollama app.exe` 会拉起 `ollama.exe`（两个都要杀）、中文 Windows 子进程编码、
   必须注入 `OLLAMA_MODELS`……从零设计会把这些坑再踩一遍。**保留。**
6. **上游机制的复用**：3 个站点适配器 + 20 余个 readerEngine + OCR provider 注册表 +
   消息契约（`MessageOf/SuccessOf/PayloadOf`）+ 图像管线（排版 7,044 行是硬活）。**保留。**
7. **arbiter/activity 那层**：它比我的从零设计厚，但它承担 M1 五态 trace 与"同页只跑一条管线"的去重，
   同时给四个调用方（图片页/阅读模式/截图/后台预取）统一了取消与进度。**保留。**
8. **双服务拆分（11436 / 11437）**：与我的从零设计一致（用户拍板），且解决真实耦合。**保留。**

# 4. 当前实现中应该改变的部分

**C1 显示模式：三来源 → 全局唯一**
当前：`TranslatorCore.displayMode` + `PhotoState.mode`（`:305,:324` 仍参与判定）+ `readingModeController.globalTranslateMode:54`；写入点 5 处。
从零：全局一个枚举；页级判 `translatedUrl != null`；阅读模式复用同一个全局量。
为什么值得改：**"切一次全页生效"现在不来自结构，只来自"两处恰好一致"** —— 漏写任一处就是偶发不同步 bug。
成本：小（读点 3 处、写点 5 处），改完加一条"两页都跟着切"的行为测试。

**C2 配置校验：两份 → 一份 parser**
当前：`image-pipeline/index.ts:390`（+`hasOnlyKeys`，115 行）与 `protocol/index.ts:554` 校验同一份 `PipelineConfig`；
加 `ocrServerBaseUrl` 时我不得不**同时改两处**（实证）。
从零：一份 `parsePipelineConfig`，消息解析与任务校验都调它。
为什么值得改：消除"改一处漏一处"这一类长期税。成本：小。

**C3 OCR：两个实现 → 一个**
当前：默认 `manga_ocr_server`（服务端），但 PaddleOCR ONNX provider + 预处理/解码 + 76MB 资产 + manifest 条目仍在，
且口径是"失败显式报错、不回退" → **第二实现永远不会被自动使用**。
从零：一个引擎。为什么值得改：消除"半保留"状态（保留的只有体量与误判空间）。
成本：中（需同时清 manifest/`models.sha256`/AMO 校验，属发布变更）。

**C4 缓存条数上限：4 持有者 → 1 权威 + 1 生效值**
当前：`settings.translationCacheLimit` → `pipelineHost.translationCacheLimit` → `…ConfiguredLimit` → `PhotoStateStore.cacheLimit`。
从零：settings 权威，随同一条配置消息下发；接收方只留"当前值"（"已生效值"用 store 的 limit 读回）。
成本：小。

**C5 弹窗状态：多源 → 一个服务状态对象**
当前：3 个 hook（各 2-3 个 `useState`）+ 组件 3 态 + 两个 3s 轮询 + `intent` 与真实状态双轨。
从零：一个 `useLocalServices()` 返回 `{state, pendingOps}`；轮询一个；"意图"= 正在进行的操作（已是集合）。
成本：小-中，收益是"这块以后不再靠叠补丁"。

**（不建议改的"看起来更优雅"的东西）**
把 `prefetchChain`+`executor` 合成一个队列、把 `pipelineHost`/`offscreenBroker` 按行数拆小、
把 arbiter 换成一个 signal —— **都属于"纸面更美、实际更险"**，见 §5。

# 7. 是否需要大规模重写？

**不需要。**

理由（每条都指向同一结论）：

1. **真正的复杂度在领域，不在结构。** 这个产品的难点是：e-hentai 的 imgkey 接龙与软导航、
   常驻画框不被站点 DOM 重建干扰、16GB 单模型驻留、Windows 进程静默启停与托盘看护、
   manga-ocr 的 beam search 置信度归属……**这些知识现在沉淀在代码与测试里**。
   重写不是"重新组织代码"，而是"把上述坑再踩一遍"，且大概率踩得更久。
2. **从零设计与现状的重合度很高（10 个决定里 7 个一致）**，重合的恰是架构骨架：
   四上下文、页身份与版本化缓存、内存优先、配置快照、上游机制复用、服务拆分、失败语义。
   差异只有 5 处，且都是**局部、有界**的（最长的一处是 OCR 第二实现，属发布决策）。
3. **护栏与测试是可复用的资产**：175 个测试文件 + 架构边界脚本（含"先擦注释再匹配"这种细节）
   + 真机验证链路。重写会让它们全部失效，而这正是本项目最有价值的部分之一。
4. **痛点是"清尾"而不是"骨架"**：第一阶段与第二阶段已证明，自造复杂度是可枚举的一小簇
   （约 1,300-1,500 行 + 6 处状态/抽象）。**局部重构能拿到全部收益，重写只会带来同等的
   不确定性 + 巨额的隐性成本。**

**唯一的例外**：如果目标从"给我自己用的阅读器"变成"多人协作的长期产品"，
那需要的是**补测试与文档、以及把 5 处局部重构做掉**，仍然不是重写。

# 8. 最终结论

**1）如果今天让我重新开发这个项目，我会保留哪些东西？**
保留骨架：四上下文分工、`pageKey` + 三版本缓存键、内存优先不落盘、配置快照随任务下发、
上游机制（站点适配器/readerEngine/ONNX 管线/消息契约/OCR provider 注册表）、
双服务拆分（OCR+翻译 / ollama 控制）、"失败必须显式"的价值观、
以及**常驻画框**与**接龙式预取**这两个领域算法。

**2）我会彻底改变哪些东西？**
只有五处，全部是局部的：**页级显示模式（删）**、**配置校验（合成一份）**、
**OCR 第二实现（删或明确标注）**、**缓存上限多镜像（合一）**、**弹窗状态/轮询（收敛）**。
加上"删掉四处死抽象与死通道"这类清尾。
