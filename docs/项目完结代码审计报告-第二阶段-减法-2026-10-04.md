# 6. 「20% 减法测试」

**结论先给：在不砍功能、不砍上游代码、不砍测试的前提下，20-30% 做不到；诚实上限是 3%。**

算术（产品代码基线 59,659 行）：

| 档 | 可减 | 占比 | 是否"无损" |
|---|---|---|---|
| A 真无损 | ~610 行 | **1.0%** | 完全无损 |
| A + B1（本地 ONNX OCR 备选） | ~1,700 行 | **2.9%** | 无损于当前行为（备选本就不自动生效） |
| 再往上只能靠：删调试/诊断面（~2,500）、删 probe（已计入）、删 `apps/web`（5,000+）、删排版/检测引擎（8,600+）、删测试（不算产品） | 3,000-15,000 行 | 5%-25% | **会砍掉功能或上游资产** |

**若被强制要求减 20%（≈11,900 行）而"功能完全不变"，唯一的"合规"方案是删 `apps/web`（5,000+）
与把 `packages/image-pipeline` 的上游能力（排版 7,044 / 检测 1,558 + 上游测试）剥离出去** —— 但那是
"把别人的代码从仓库里移走"，不是真的简化，而且会破坏与上游对账的能力。**不建议。**

所以本阶段给出的减法清单是 §1 的 A 档 + §2 的 1-10 + §3 的状态收敛（合计约 **1,300-1,500 行 + 6 处状态/抽象**），
这已经覆盖了**所有"无损且降复杂"的空间**。

# 7. 奥卡姆剃刀最终结论

**1）哪些复杂度是业务真正需要的？**
- 排版引擎（7,044 行）：漫画去字后重排中文，断行/字距/竖排是硬需求。
- 检测/气泡/消字 ONNX 链路 + `ModelRuntime`/worker（`detector.ort`/`bubble.onnx`/`aot_inpaint`）：浏览器侧必须自己推理。
- 跨四进程的数据流（content→background→offscreen + 本地服务 11436 + ollama 11437）：这是扩展 + 本地服务架构的必然。
- 站点适配器 / readerEngines / 消息契约：上游既有机制，且多站点确实各有差异。
- `PhotoStateStore.protect/release`、预取链的"逐跳接龙"（imgkey 只在前一页 JSON 里）：**真实约束**，不是设计问题。

**2）哪些复杂度是代码自己制造的？**
- 显示模式三来源（含判定需两处同时成立）→ 可直接减成 1。
- 同一份配置形状两处校验 → 可直接减成 1。
- `isRecord` ×26、环回校验 ×3（口径还不一致）、`clamp` ×5、quad/box ×2。
- `localPipelineClient` 两段 Port 会话、`screenshotController` 两个同构大函数。
- 端口常量多真源、缓存上限 4 个镜像。
- 死抽象 4 个（HostThrottle / PageCacheManager / 窗口规划 / 死消息通道）。
- 弹窗两个 3s 轮询 + `intent` 与真实状态双轨。

**3）哪些代码明显属于历史包袱？**
- 四处死抽象（上面）。其中 `PageCacheManager`（M2 的四层缓存）与 `planPrefetchWindow`（旧调度窗口）
  是**被后续实现取代后没清场**；`HostThrottle` 是**从未接线**；`mt:translation-cache` 是**关停后留管道**。
- 上游兼容层：`recoverPipelineRecord` 旧 schema 恢复、prompt 模板旧版本迁移、
  `settingsStore` 三代旧存档兼容 —— **这些是必要的包袱，建议保留**。
- 文档包袱：`NEED_FROM_USER.md` 整篇过期、README 的"shinobu 一行不改"与"11436 能管模型"。

**4）哪些东西应该删除？**
§1 A 档全部（~610 行产品 + 测试/probe/杂物）+ 决策后删 B1（本地 ONNX OCR 备选，~1,100 行 + 76MB 资产）。
**加上一处必须做的选择**：`mt:translation-cache` 要么删、要么在代码与文档里显式标注"未启用"——
**不要继续停在"开关关着"**。

**5）哪些东西应该保持不动？**
- **`prefetchChain` 的三条推进机制**：重写风险 > 收益（它被真机问题逼出来，注释完整）。
- **排版/检测/消字引擎与上游兼容层**：改了就是砍功能或破坏对账。
- **诊断/遥测面**：你实际在用（失败排查就靠它）。
- **`router.ts` 类型体操、两个服务 Handler 的样板、`vram.py` 多层卸载、`ocr.py` 多层回退**：
  各自的重复/分层都有独立理由，合并只会增加耦合。
- **`PhotoStateStore` 的 limit/protect 机制、`pipelineContext` 五态 trace**：前者是必要的防淘汰，后者只写不读但体量极小（当调试探针留着）。

> 一句话总结：
> **这个项目的复杂度大体是"业务要求 + 上游既有"的，自己制造的复杂度是可枚举的一小簇（约 1,300-1,500 行 + 6 处状态/抽象）。把它清掉就能显著降低维护成本；再往下砍，砍到的是功能，不是复杂度。**
