## 1. 目标与非目标

**目标**
1. 用户侧成本 ≈ 0：**一次点击**得到可提交的诊断材料，不需要先去勾开关、也不需要知道日志在哪。
2. 我们拿到就能回答四件事：**哪一跳、什么错、什么环境、能否复现**。
3. 扩展（shinobu 侧）与本机服务端（11436/11437）**口径一致**，靠同一份 schema 与同一个贯穿 ID 对齐。
4. 隐私可承诺：**默认日志不含漫画原文/译文**。

**非目标**
- 不做 APM / 远端上报。**永不外发**，只在用户主动导出时离开本机。
- 不做性能剖析工具（jank 之类保留，但并入统一事件流，不另起门户）。
- 不在本文改造 shinobu 的业务逻辑 —— 只动日志采集面。

## 2. 反推：先定"要回答什么"，再定字段

不看现有字段，先列问题（§3 的病灶大多源于"先有字段、后补需求"）：

| # | 要回答的问题 | 真正需要的数据 | 需要原文？ |
|---|---|---|---|
| Q1 | 装不起来 / 服务起不来 | 启动阶段事件、端口探活、模型加载结果、Python 与浏览器版本、路径权限 | 否 |
| Q2 | 翻页慢 / 卡 | 各阶段耗时、OCR 与 LLM 服务端自报耗时、队列深度、jank | 否 |
| Q3 | 某页翻译失败 | `failure{stage, code, retryable, cause}`，**必须含 pipeline 之外** | 否 |
| Q4 | 翻译质量差 | 原文、译文、模型名、术语表版本、prompt 变体 | **是（唯一场景）** |
| Q5 | 图片不显示 / 格式错 | 下载事件：host、referer 是否生效、字节数、content-type、重试次数 | 否 |

**结论（决定分层）**：除 Q4 外排障都不需要原文。
→ 原文/译文/图片字节归 **L1**，默认**打码**（只留行数、字符数、语言），用户勾「包含原文」才全量。**已拍板。**

## 3. 现状病灶（2026-10-05 全项目审计结论）

### 3.1 八个出口，各写各的 schema

| 侧 | 出口 | 形态 | 开关 / 默认 |
|---|---|---|---|
| 扩展 | 诊断日志 `mt:diagnostic-log-event` | 事件流（环形 2000 条 → 手动下载） | `enableDebugLog` **关** |
| 扩展 | 整页日志 `offscreen/pageLog.ts` → `POST /log/page` | 一页一条聚合 | `pageLogEnabled` **开** |
| 扩展 | DOM dataset（`data-m5-chain` / `m5-restore` / `m1-trace`） | 实时快照，**页面脚本可读** | **无开关** |
| 扩展 | `console.*` ×25 | 控制台 | 无级别策略 |
| 服务端 | `logs/<model>/YYYY-MM-DD.log` | 人类可读行 | **恒开** |
| 服务端 | `.trace.jsonl` | 阶段耗时 | `DMB_TRACE` **开** |
| 服务端 | `.image.jsonl` | 翻译归档（含逐行 jp/zh） | **恒开** |
| 服务端 | `logs/pages/*.pages.jsonl` | 整页记录 | `DMB_PAGE_LOG` **开** |

### 3.2 五条结构性问题

1. **出口太多**：任何"统一"若只是再加一层聚合，等于造第 9 个出口 —— 这是必须拒绝的做法。
2. **三种形态并存**（事件流 / 聚合记录 / 实时快照），靠人脑对齐，跨仓库尤其对不上。
3. **采集点焊在业务代码里**：`emitDiagnosticLog` 散在 9 个文件、pageLog 在 pipelineHost、dataset 在 3 处。加采集点 = 改业务。
4. **失败不是第一公民**：只记终态。**pipeline 之外抛的错（图片字节下载失败）完全隐身** —— 94 页那个 bug 就是这么被拖长的。
5. **开启方式与求助路径不匹配**：排障主力（诊断日志）默认关 + 手动下载，而默认开的那些又不覆盖失败路径。

## 4. 目标结构：先减后加，收敛成 1 + 1

```
        一条事件流（统一 schema，两仓库同源）  ──▶  一个出口（支持包，一键导出）
```

- **一条事件流**：所有可排障信息都变成 append-only 事件，扩展与服务端写的是**同一份 schema**。
- **一个出口**：支持包 = 事件流切片 + 环境快照 + 设置快照（脱敏）+ 人可读摘要。

### 4.1 分层

| 层 | 内容 | 默认 |
|---|---|---|
| **L0** | 环境快照、设置快照（脱敏）、**所有失败**、阶段耗时、计数、版本 | **常开**（用户零操作） |
| **L1** | 逐行原文/译文、图片字节与尺寸、DOM 级细节、服务端日志全文 | **关**，导出时默认打码，勾选才含 |

### 4.2 出口形态：**单文件 JSON**（已定）

支持包是一个 JSON 文件 `dmb-support-<ISO>.json`，可以直接贴进 issue：

```jsonc
{
  "v": 2, "generatedAt": "…", "exporter": { "repo": "dmb", "commit": "…" },
  "env":      { /* 扩展版本 / 服务端 commit / 模型 / OCR 引擎 / 浏览器 / 显存 */ },
  "settings": { /* 脱敏后的设置快照 */ },
  "summary":  { /* 人可读结论：失败 Top N、最近 10 次运行、错误分类计数 */ },
  "events":   [ /* 统一 schema 的事件（按 requestId 可串成时间线） */ ],
  "server":   { "tail": ["…最近 N 行…"], "path": "…" },
  "privacy":  { "containsOriginalText": false, "redacted": ["settings.*key", "url.query"] }
}
```

丢弃 zip 的理由：issue 里只能贴文本，多文件还要人去下载解压；单文件 JSON 既能机读也能一眼看 `summary`。

### 4.3 上报方式：**批量异步，绝不进关键路径**（已定）

硬约束（用户口径：**不影响翻译任务的速度**）：

1. `emit()` 必须是**同步 O(1)**：只往内存环形缓冲 push 一个对象，**不做 `JSON.stringify`、不发网络、不碰存储**。
2. 落盘/上报在**空闲时批量做**：满 32 条或 500 ms 触发一次 flush，`fetch(..., {keepalive:true})` **fire-and-forget**，
   **永不 `await`**；flushing 期间到达的事件继续进缓冲，不阻塞。
3. 缓冲有上限（512 条），满了丢最旧的并给 `dropped` 计数（丢事件可以，卡住翻译不行）。
4. 开关关闭时整套退化成 **no-op**（连那层函数调用都不产生）。
5. **导出时才做序列化**——这是唯一允许 `JSON.stringify` 全量事件的时刻，且由用户点击触发。

## 5. 统一 schema（两仓库同源）

```jsonc
{
  "v": 2,                 // schema 版本，只增不减；未知字段原样透传
  "ts": "2026-10-05T16:10:00+08:00",
  "seq": 1287,            // 进程内单调序号（对账乱序用）
  "sessionId": "s-…",     // 一次浏览器会话
  "runId": "r-…",         // 一次翻译任务（沿用 shinobu 既有）
  "pageKey": "3193401-94",// 站点内页身份（e-hentai: gid-page）
  "requestId": "q-…",     // ★ 跨进程贯穿 ID，见 §6
  "level": "error",       // debug | info | warn | error
  "kind": "failure",      // 见 §7 事件清单
  "where": { "repo": "extension", "module": "imageDownloader", "fn": "downloadSerialized" },
  "what":  { "stage": "fetch", "host": "…hath.network", "refererApplied": true },
  "err":   { "type": "TypeError", "message": "Failed to fetch", "code": "IMAGE_FETCH_FAILED" },
  "dur_ms": 14572
}
```

约定：
- `what` **自由但需登记**：每个 `kind` 的字段在本文 §7 登记，新增 kind 必须同步更新本文。
- 脱敏规则**沿用 shinobu 既有**（密钥键名 → `[REDACTED]`、URL 只留 origin+pathname、base64/blob 打码），服务端照抄同一套（现状服务端没有）。
- 版本策略：`v` 只增；读取端忽略未知字段（与 `pagelog.py` 现行策略一致）。

## 6. requestId 贯通（两侧对齐的唯一凭据）

1. 扩展为**每个跨进程请求**生成 `requestId`（`q-<uuid8>`）。
2. 发往 `/ocr`、`/v1/chat/completions`、`/log/events` 时带请求头 `X-DMB-Request-Id`。
3. 服务端**必须回显同一值**（响应头 + 自己那一行日志）。
4. 支持包按 `requestId` 把扩展侧事件与服务端事件串成一条时间线。

> **M1 实际做法（与上文有一处偏差，记录在案）**：由**服务端**生成并回显
> （`eventlog.resolve_request_id()`：请求头带了就沿用，没带就生成一个，`X-DMB-Request-Id` 回显），
> 扩展侧拿到后记进 `page.completed` 的 `what.requestIds`。
> 理由：扩展若要"主动生成"，得改 `packages/image-pipeline` 里的 OCR provider —— 那是对上游的接触点，
> 按 `UPSTREAM_PATCHES.md` 的纪律应尽量少动。**效果一样**（两侧一定存在同一个 ID），
> 客户端主动生成留到 M2 再评估。

**M1 已落地的三个出口**：
- `POST /ocr` → `timing.requestId` + 响应头 + 服务端 `ocr.call` 事件
- `POST /v1/chat/completions` → `dmb_timing.requestId` + 响应头 + 服务端 `llm.call` / `failure` 事件
- `POST /log/events` → 事件缺 `requestId` 时用本次请求的 ID 兜底（不让它变成"无主"）

> 现状缺的就是这一条：两侧各有日志，但没有办法证明"这两行是同一次请求"。

## 8. 失败成为第一公民（治本条款）

> **纪律：任何"要抛异常/要返回失败"的出口，必须先发一条 `kind:"failure"` 事件。**

覆盖范围（现状全部或部分缺失）：图片字节下载、DNR 规则安装、消息通道、OCR、翻译、排版、还原。
这条成立之后，"图片下载失败在日志里完全隐身"这类问题在架构上不再可能发生 —— 不需要靠每个调用点自觉。

验收方式：新增一条架构检查（§10），对每个已知抛出点断言存在 failure 事件。

### 9.1 `data-m5-chain` 是什么（问答）

**它是预取链的遥测快照**，写在 `documentElement.dataset.m5Chain`（`shinobu/apps/extension/src/content/index.ts:141`），
内容是把三份状态合成一个 JSON 字符串：

| 字段 | 来源 | 含义 |
|---|---|---|
| `chain` | `prefetchChain.ts` 快照 | `enabled / disabledReason / knownCount / requested / received / duplicates / failed / farthestPage / lastPageKey` |
| `dispatch` | `showpageClient.ts` 统计 | `ok / fail / failStreak / pending / circuitOpen` |
| `executor` | `prefetchExecutor.ts` 快照 | `knownUrls / submitted / skippedBusy / skippedNoImage / outOfWindow / queued[] / active` |
| `showkeyFound` | `content/index.ts` | showkey 是否提取到 |

**当时为什么要挂在 DOM 上**：主世界与隔离世界 `window` 不共享，DOM 属性是**唯一双方都能看见**的地方，
外部探针（不注入我们代码）才能读到。这是它的历史价值。

**为什么现在要收口**：①它把内部状态以明文 JSON 暴露给页面上的任何脚本；②它是"第 3 个日志出口"，
与事件流、整页日志三套并存。所以改写成：**默认不写**，要看的时候开调试开关，长期信息走 `prefetch.chain` 事件。

## 12. 迁移步骤（每步可停、每步可验）

| 步 | 内容 | 验收 |
|---|---|---|
| **M0** | 立 schema 与事件 sink；新代码走新通道，旧的**暂时并存** | 新事件能被导出；旧功能全部不变 |

### M2 已落地（2026-10-05）：failure 覆盖 background 全部抛出点

**为什么先做它**：94 页那类错误的病根是**结构性静默** —— 原图字节下载失败抛在
`executeLocalPipeline` **之前**，offscreen 的 pipelineHost 根本没跑到，整页日志只记终态，
于是三家日志 0 命中。用户看到"翻译失败"，我们拿到日志却查不到任何一行。

**两条互补的上报路径（刻意不重复）**：

| 位置 | 覆盖 | 信息量 |
|---|---|---|
| `imageDownloader` 的 `onFailure`（**第一现场**） | 下载失败 | **结构化**：`imageHost` / 逐候选 `attempts[{index,hostname,reason,durationMs,refererApplied,dnrError}]` / `attemptCount` / `dur_ms` |
| `routeBackgroundMessage` 的兜底（**网**） | background 侧**任何**消息类型的抛出点 | 消息类型 + 错误串 |

- 兜底**排除 `mt:download-image`**：后者已有带明细的第一现场上报，不再记一条只剩字符串的 ——
  重复日志会稀释真正的信号，那是屎山的开始。
- 两处都是**包一层**（`downloadSerialized` 包 `downloadCandidates`、`routeBackgroundMessage`
  包 `dispatchBackgroundMessage`），不是在每个 `throw` 前逐个加一句。
  逐个加必然漏（以后新增抛出点谁还记得加），包一层后"抛出"与"上报"绑在一起。

**pageKey / runId 怎么带过去的**：下载请求以前只带 `imageUrl`，事件流里只能靠时间戳猜是哪一页。
现在 `mt:download-image` 多带两个**可选**字段（content 侧本来就有 `request.pageKey` 与
`diagnosticRunId`），一路传到抛出点。缺失时留空，不影响下载本身。

**隐私**：`imageUrl` 进日志前只保留 `origin + pathname` —— 图片地址常带逐请求签名
（`keystamp=`），整条 URL 不能进日志（日志是要贴给别人看的）。测试里有断言守着。

**共享出口**：`resolveEventLogBase` + `createHttpEventLogSink` 抽到 `shared/eventLogSink.ts`，
background 与 offscreen 用同一份。此前 pipelineHost 里那份地址推导是本地私有的，两侧各写一遍
迟早漂移（踩过：地址曾搭在 OCR 引擎条件下，换引擎后整条旁路静默失效）。

**M2b 已落地（2026-10-05）：content 侧接入**

内容脚本**发不出 HTTP** —— 它的 `fetch` 受页面 CSP（`connect-src`）约束，到不了
`http://127.0.0.1:11436`；只有 background / offscreen 用扩展自己的 CSP 才发得出去。
所以新增 `mt:event-log` 消息（content → background），**出口实现仍然只有一处**：

- `shared/messages.ts`：`EventLogPushMessage`（`events: DmbEventInput[]`）+ 校验 + 响应带 `accepted`。
- `background/messages/router.ts`：`services.eventLog.push(events)` —— **只收不记**，真正落盘在 background 出口。
- `content/core/telemetry/contentEventLog.ts`：内容侧客户端。
  本地编号（`v/ts/seq/sessionId`）**交给 background 之前剥掉**，由 background 统一打点 ——
  否则两边各打一套编号，事件流里会出现两个 `sessionId` 打架。
- 首个接入点：`imageTranslationExecution.ts` 的**准备阶段失败**
  （`IMAGE_TRANSLATION_SETTINGS_INVALID`，offscreen 根本不知道，以前完全静默）。

**内容侧的开关取舍（记录在案）**：内容侧拿不到 settings（配置的持有者是 background），
所以没有"是否开启"的本地依据。做法是 `enabled: true` 但**只在失败路径 emit** ——
成功路径一条都不记。代价被限定在"本来就要弹错误 UI 的那一次异常"上：
一次 O(1) 内存 push + 最多一次异步消息往返，不影响正常翻译的任何一跳。

**刻意不重复记**：下载失败归 background 的第一现场（带结构化候选明细），
pipeline 内失败归 offscreen。内容侧只报**只有它知道**的那种失败。三处代码里都写了注释说明原因。

### M3 已落地（2026-10-05）：支持包一键导出

**分工：事件那一半由服务端出，扩展只补自己才知道的两段。**

理由（写在这里，免得以后有人"顺手"把它挪回扩展）：扩展侧的事件缓冲是**过路**的 ——
满 32 条或 500ms 就 flush 走，job 结束还会强制 flush。任何时刻去内存里取，拿到的通常是空的。
事件真正的家是服务端的 `logs/events/YYYY-MM-DD.events.jsonl`。让扩展去攒，等于攒一个空壳。

| 半边 | 产物 |
|---|---|
| 服务端 `server/support.py` + `GET /support` | `window`（读了哪些文件/总行数/是否截断）、`summary`（**由 events 现场算出**）、`events`、`server`（health + tail + eventLogPath）、`privacy` |
| 扩展 `shared/supportBundle.ts` + 弹窗按钮 | `env`（UA/平台/语言/时区）、`settings`（弹窗手里那份已是脱敏投影）、再拼上服务端那半 → `downloadJson` 落成 `dmb-support-<ISO>.json` |

**三条纪律（都落到了代码与测试里）**：

1. **「没采到」≠「采到了但为空」**（诊断器铁律）。服务端不可达时写 `server: null` +
   `serverError`，`summary` 明写"未取到服务端事件，以下统计不可用"，**绝不给空壳** ——
   否则看日志的人会以为"事件确实一条都没有"。
2. **`summary` 与 `events` 同源**：summary 由 events 现场算，不另开一套统计，
   避免"结论与证据不一致"。失败按 `模块/错误码` 归类（不按整句 message —— 里面带 host/耗时，
   同一类错会长出几十个 key，Top N 就失去意义）。
3. **截断如实标注**：超出 `limit` 只留最近一批，并写 `window.truncated` ——
   不许给人一个看着完整、其实被截断还没说的文件。

**只认本机地址**（`resolveSupportServerBase`）：LLM 的 base 可能是 `api.openai.com`，
拿它拼 `/support` 会把本机日志发给第三方或得到一个 404。不是 loopback 就退回默认端口。

**不受"日志记录"开关限制**：设计 §1 要求用户侧成本 ≈ 0，排障材料不该藏在调试模式背后；
按钮只在"调试选项展开"里露出，但点下去不需要先去勾任何开关。

**验收（真机跑通，2026-10-05 17:32）**：服务端 11436 重启后 `GET /support` 200；
投一条下载失败到 `/log/events` → 支持包里出现该事件，且能回答 Q3（`pages.failed: 1`，
`pageKey 1234567-94`）/ Q5（`imageHost` + 逐候选 `attempts`）/ Q6（health + eventLogPath）；
签名参数无泄漏（`keystamp` 未出现）。

### ⚠️ 同批修掉的真缺陷：事件流曾会把日志发到云端

做 M3 时回头核 `resolveEventLogBase`，发现它只做 `new URL(llmBaseUrl).origin`
而**没有 loopback 校验** —— 而 `llmBaseUrl` 在云端模式下正是 `https://api.openai.com/v1`。
后果：每次 flush 都会把带失败详情、文件路径、主机名的事件 **POST 到第三方**，
且 sink 吞错、**全程静默**，与 §1「日志永不外发」直接冲突。

已修（`shared/eventLogSink.ts`）：两条推导路径都**必须落在 loopback**
（`127.0.0.1` / `localhost` / `[::1]`），否则返回 undefined，事件流整体关成 no-op ——
**宁可没有日志，也不外发一个字节**。顺带修好了**整页日志**的同类外发：
`pipelineHost.resolvePageLogBase` 已委托给同一个函数，以前同样会拼出云端地址。

护栏：`tests/shared/eventLogSink.test.ts` 有专门的用例守着
（云端 base / 内网 IP / 云端 OCR base 带偏 → 全部 undefined）。

### M4 第一步已落地（2026-10-05）：DOM 遥测收口

§9 的第一项。三处**无条件**写 DOM 的遥测全部改走闸门：

| 原写入点 | 属性 | 现在 |
|---|---|---|
| `content/index.ts` `publishTelemetry` | `data-m5-chain` | `publishDomTelemetry('m5Chain', …)` |
| `imageTranslationController.ts` `publishRestoreTelemetry` | `data-m5-restore` | `publishDomTelemetry('m5Restore', …)` |
| `imageTranslationExecutionArbiter.ts` `publishTrace` | `data-m1-trace` | `publishDomTelemetry('m1Trace', …)` |

新增 `shared/domTelemetry.ts`（模块级闸门，零 import）+ 设置项 **`telemetryDomEnabled`（默认关）**。

**通道选择**：开关搭已有的 `mt:prefetch-config` / `-sync` 回读，**没有新开消息**。
理由：这条消息本来就是"内容脚本运行时开关"的载体（内容脚本拿不到 settings，
所有运行时开关只能走它），而三处遥测都写在内容脚本里。单独开一条通道，
只会多一处将来必然与它漂移的真相。

**两个容易反的地方，已经写成注释与用例**：

1. `telemetryDomEnabled` 与 `prefetchEnabled` 的**缺字段语义相反**，这不是笔误：
   判断标准统一为「**缺字段时的行为必须等于用户期望的安全默认**」。
   `prefetchEnabled` 缺字段会落回"开"（把用户刚关掉的预载悄悄打开）→ 必须**必填**；
   `telemetryDomEnabled` 缺字段落回"关"（不暴露内部状态）→ 可以**可选**。
2. 关闭时**连 `JSON.stringify` 都不发生**（闸门第一行返回）。三份 snapshot 的组装
   就在调用点，闸门若晚一步返回，热路径照样白干 —— 有用例 `spyOn(JSON, 'stringify')` 守着。

**护栏（§10 第 2 条已实现）**：`check-extension-architecture.mjs` 新增
「里程碑 DOM 遥测必须走闸门」（只认 `m<数字>`，`data-mt-ehentai-anchor` 那类功能属性不在管辖内）。
**做了反向验证**：临时插一行 `dataset.m9Probe = '1'` → 护栏立刻红；删除后恢复绿。

**探针兼容**：`probe/m5-flashdiag/README.md` 与 `probe/m4-diag` 的"未读到遥测"提示
都已更新 —— 现在最常见的未读到原因是**没勾 DOM 遥测**，其次才是扩展没装/版本旧。
不更新的话，下一个人会被引偏到"扩展是不是坏了"。

### M4 第四步已落地（2026-10-05）：整页日志 + `/log/page` 下线

**最需要小心的一步**：整页日志不是"没用的旧东西"，它带着一整套踩坑换来的口径。
所以下线方式是**把口径搬走再拆**，而不是删掉：

| 保住的东西 | 现在在哪 |
|---|---|
| `total_ms` 只在 `parallel` 在场时跳过子阶段（否则 Translate 算两遍、虚高 70%） | `offscreen/pipelineTelemetry.ts` 的 `summarizeStages()` |
| 失败/取消只认**实时轨迹**（pipeline 抛异常后 `stageTimings` 就没了） | 同上 + `failure.what.stages` |
| `errorStage` **命中轨迹才**标 `failed`，不硬标 | 同上 |
| 逐行译文的权威来源是 `captured`（`record.translations` 的 `translatedText` 恒为空串） | `toLines()` |

`pageLog.ts` / `pagelog.py` / `POST /log/page` 全部删除；
`pageLogEnabled` 这个设置项**保留但语义迁移**为 L1 开关（决定要不要附带原文），
弹窗文案改成「日志含原文/译文（详细层）」——保留字段名是为了不做一次牵动老用户 storage 的迁移。

**采集点的闸门也得跟着搬**：`markStage`（阶段轨迹）原来的门控是 `pageLogEnabled`（L1），
但 `page.completed.stages` 是 **L0** 数据 —— 用户关掉"含原文"，阶段耗时就跟着没了。
现在门控改为**事件流的闸门**（`eventLogEnabled`），关闭时依旧整体 no-op。

**顺带修掉一个会误导人的收尾**：`/log/page` 删掉后会掉进 passthrough 转发给 Ollama，
返回一个 **502** —— 看起来像"服务挂了"，排查的人会先去查服务。现在 `/log/*` 在 GET/POST
两端都直接返回 **404 + 明确说明**（"M4 起只有 /log/events"）。
