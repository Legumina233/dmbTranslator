## 1. 目标与非目标

**目标**
1. 用户侧成本 ≈ 0：**一次点击**得到可提交的诊断材料，不需要先去勾开关、也不需要知道日志在哪。
2. 我们拿到就能回答四件事：**哪一跳、什么错、什么环境、能否复现**。
3. 扩展（shinobu 侧）与本机服务端（11436/11437）**口径一致**，靠同一份 schema 与同一个贯穿 ID 对齐。
4. 隐私可承诺：**默认日志不含漫画原文/译文**。

**非目标**
- 不做 APM / 远端上报。**永不外发**，只在用户主动导出时离开本机。
- 不做性能剖析工具（jank 之类保留，但并入统一事件流，不另起门户）。
- 不在本文改造 shinobu 的业务逻辑 —— 只动日志采集面。

## 2. 反推：先定"要回答什么"，再定字段

不看现有字段，先列问题（§3 的病灶大多源于"先有字段、后补需求"）：

| # | 要回答的问题 | 真正需要的数据 | 需要原文？ |
|---|---|---|---|
| Q1 | 装不起来 / 服务起不来 | 启动阶段事件、端口探活、模型加载结果、Python 与浏览器版本、路径权限 | 否 |
| Q2 | 翻页慢 / 卡 | 各阶段耗时、OCR 与 LLM 服务端自报耗时、队列深度、jank | 否 |
| Q3 | 某页翻译失败 | `failure{stage, code, retryable, cause}`，**必须含 pipeline 之外** | 否 |
| Q4 | 翻译质量差 | 原文、译文、模型名、术语表版本、prompt 变体 | **是（唯一场景）** |
| Q5 | 图片不显示 / 格式错 | 下载事件：host、referer 是否生效、字节数、content-type、重试次数 | 否 |
| Q6 | 环境对不上 | 扩展版本、服务端 commit、模型名、OCR 引擎、关键设置快照 | 否 |

**结论（决定分层）**：除 Q4 外排障都不需要原文。
→ 原文/译文/图片字节归 **L1**，默认**打码**（只留行数、字符数、语言），用户勾「包含原文」才全量。**已拍板。**

## 3. 现状病灶（2026-10-05 全项目审计结论）

### 3.1 八个出口，各写各的 schema

| 侧 | 出口 | 形态 | 开关 / 默认 |
|---|---|---|---|
| 扩展 | 诊断日志 `mt:diagnostic-log-event` | 事件流（环形 2000 条 → 手动下载） | `enableDebugLog` **关** |
| 扩展 | 整页日志 `offscreen/pageLog.ts` → `POST /log/page` | 一页一条聚合 | `pageLogEnabled` **开** |
| 扩展 | DOM dataset（`data-m5-chain` / `m5-restore` / `m1-trace`） | 实时快照，**页面脚本可读** | **无开关** |
| 扩展 | `console.*` ×25 | 控制台 | 无级别策略 |
| 服务端 | `logs/<model>/YYYY-MM-DD.log` | 人类可读行 | **恒开** |
| 服务端 | `.trace.jsonl` | 阶段耗时 | `DMB_TRACE` **开** |
| 服务端 | `.image.jsonl` | 翻译归档（含逐行 jp/zh） | **恒开** |
| 服务端 | `logs/pages/*.pages.jsonl` | 整页记录 | `DMB_PAGE_LOG` **开** |

### 3.2 五条结构性问题

1. **出口太多**：任何"统一"若只是再加一层聚合，等于造第 9 个出口 —— 这是必须拒绝的做法。
2. **三种形态并存**（事件流 / 聚合记录 / 实时快照），靠人脑对齐，跨仓库尤其对不上。
3. **采集点焊在业务代码里**：`emitDiagnosticLog` 散在 9 个文件、pageLog 在 pipelineHost、dataset 在 3 处。加采集点 = 改业务。
4. **失败不是第一公民**：只记终态。**pipeline 之外抛的错（图片字节下载失败）完全隐身** —— 94 页那个 bug 就是这么被拖长的。
5. **开启方式与求助路径不匹配**：排障主力（诊断日志）默认关 + 手动下载，而默认开的那些又不覆盖失败路径。

## 4. 目标结构：先减后加，收敛成 1 + 1

```
        一条事件流（统一 schema，两仓库同源）  ──▶  一个出口（支持包，一键导出）
```

- **一条事件流**：所有可排障信息都变成 append-only 事件，扩展与服务端写的是**同一份 schema**。
- **一个出口**：支持包 = 事件流切片 + 环境快照 + 设置快照（脱敏）+ 人可读摘要。

### 4.1 分层

| 层 | 内容 | 默认 |
|---|---|---|
| **L0** | 环境快照、设置快照（脱敏）、**所有失败**、阶段耗时、计数、版本 | **常开**（用户零操作） |
| **L1** | 逐行原文/译文、图片字节与尺寸、DOM 级细节、服务端日志全文 | **关**，导出时默认打码，勾选才含 |

### 4.2 出口形态：**单文件 JSON**（已定）

支持包是一个 JSON 文件 `dmb-support-<ISO>.json`，可以直接贴进 issue：

```jsonc
{
  "v": 2, "generatedAt": "…", "exporter": { "repo": "dmb", "commit": "…" },
  "env":      { /* 扩展版本 / 服务端 commit / 模型 / OCR 引擎 / 浏览器 / 显存 */ },
  "settings": { /* 脱敏后的设置快照 */ },
  "summary":  { /* 人可读结论：失败 Top N、最近 10 次运行、错误分类计数 */ },
  "events":   [ /* 统一 schema 的事件（按 requestId 可串成时间线） */ ],
  "server":   { "tail": ["…最近 N 行…"], "path": "…" },
  "privacy":  { "containsOriginalText": false, "redacted": ["settings.*key", "url.query"] }
}
```

丢弃 zip 的理由：issue 里只能贴文本，多文件还要人去下载解压；单文件 JSON 既能机读也能一眼看 `summary`。

### 4.3 上报方式：**批量异步，绝不进关键路径**（已定）

硬约束（用户口径：**不影响翻译任务的速度**）：

1. `emit()` 必须是**同步 O(1)**：只往内存环形缓冲 push 一个对象，**不做 `JSON.stringify`、不发网络、不碰存储**。
2. 落盘/上报在**空闲时批量做**：满 32 条或 500 ms 触发一次 flush，`fetch(..., {keepalive:true})` **fire-and-forget**，
   **永不 `await`**；flushing 期间到达的事件继续进缓冲，不阻塞。
3. 缓冲有上限（512 条），满了丢最旧的并给 `dropped` 计数（丢事件可以，卡住翻译不行）。
4. 开关关闭时整套退化成 **no-op**（连那层函数调用都不产生）。
5. **导出时才做序列化**——这是唯一允许 `JSON.stringify` 全量事件的时刻，且由用户点击触发。

## 5. 统一 schema（两仓库同源）

```jsonc
{
  "v": 2,                 // schema 版本，只增不减；未知字段原样透传
  "ts": "2026-10-05T16:10:00+08:00",
  "seq": 1287,            // 进程内单调序号（对账乱序用）
  "sessionId": "s-…",     // 一次浏览器会话
  "runId": "r-…",         // 一次翻译任务（沿用 shinobu 既有）
  "pageKey": "3193401-94",// 站点内页身份（e-hentai: gid-page）
  "requestId": "q-…",     // ★ 跨进程贯穿 ID，见 §6
  "level": "error",       // debug | info | warn | error
  "kind": "failure",      // 见 §7 事件清单
  "where": { "repo": "extension", "module": "imageDownloader", "fn": "downloadSerialized" },
  "what":  { "stage": "fetch", "host": "…hath.network", "refererApplied": true },
  "err":   { "type": "TypeError", "message": "Failed to fetch", "code": "IMAGE_FETCH_FAILED" },
  "dur_ms": 14572
}
```

约定：
- `what` **自由但需登记**：每个 `kind` 的字段在本文 §7 登记，新增 kind 必须同步更新本文。
- 脱敏规则**沿用 shinobu 既有**（密钥键名 → `[REDACTED]`、URL 只留 origin+pathname、base64/blob 打码），服务端照抄同一套（现状服务端没有）。
- 版本策略：`v` 只增；读取端忽略未知字段（与 `pagelog.py` 现行策略一致）。

## 6. requestId 贯通（两侧对齐的唯一凭据）

1. 扩展为**每个跨进程请求**生成 `requestId`（`q-<uuid8>`）。
2. 发往 `/ocr`、`/v1/chat/completions`、`/log/events` 时带请求头 `X-DMB-Request-Id`。
3. 服务端**必须回显同一值**（响应头 + 自己那一行日志）。
4. 支持包按 `requestId` 把扩展侧事件与服务端事件串成一条时间线。

> 现状缺的就是这一条：两侧各有日志，但没有办法证明"这两行是同一次请求"。

## 8. 失败成为第一公民（治本条款）

> **纪律：任何"要抛异常/要返回失败"的出口，必须先发一条 `kind:"failure"` 事件。**

覆盖范围（现状全部或部分缺失）：图片字节下载、DNR 规则安装、消息通道、OCR、翻译、排版、还原。
这条成立之后，"图片下载失败在日志里完全隐身"这类问题在架构上不再可能发生 —— 不需要靠每个调用点自觉。

验收方式：新增一条架构检查（§10），对每个已知抛出点断言存在 failure 事件。

### 9.1 `data-m5-chain` 是什么（问答）

**它是预取链的遥测快照**，写在 `documentElement.dataset.m5Chain`（`shinobu/apps/extension/src/content/index.ts:141`），
内容是把三份状态合成一个 JSON 字符串：

| 字段 | 来源 | 含义 |
|---|---|---|
| `chain` | `prefetchChain.ts` 快照 | `enabled / disabledReason / knownCount / requested / received / duplicates / failed / farthestPage / lastPageKey` |
| `dispatch` | `showpageClient.ts` 统计 | `ok / fail / failStreak / pending / circuitOpen` |
| `executor` | `prefetchExecutor.ts` 快照 | `knownUrls / submitted / skippedBusy / skippedNoImage / outOfWindow / queued[] / active` |
| `showkeyFound` | `content/index.ts` | showkey 是否提取到 |

**当时为什么要挂在 DOM 上**：主世界与隔离世界 `window` 不共享，DOM 属性是**唯一双方都能看见**的地方，
外部探针（不注入我们代码）才能读到。这是它的历史价值。

**为什么现在要收口**：①它把内部状态以明文 JSON 暴露给页面上的任何脚本；②它是"第 3 个日志出口"，
与事件流、整页日志三套并存。所以改写成：**默认不写**，要看的时候开调试开关，长期信息走 `prefetch.chain` 事件。

## 10. 护栏（防止再堆）

沿用仓库既有 `scripts/check-extension-architecture.mjs` 的机制，新增三条规则：

1. 业务代码**禁止裸 `console.*`**（白名单：崩溃兜底 1 处）。
2. **禁止新增 `dataset.m*` 遥测**（DOM 不是日志载体）。
3. **禁止新增第二个日志出口**（新代码只有事件流这一条路）。

外加一条正向断言：已知抛出点必须能找到对应的 failure 事件（§8 验收）。

## 11. 隐私与体量

- **L1 默认打码**：只留行数、字符数、语言；用户勾「包含原文」才全量。**已拍板。**
- URL 与凭据沿用 shinobu 脱敏；服务端补同一套。
- **体量（现状完全没有）**：事件环形上限（扩展侧沿用 2000）、单文件超过阈值分片、**保留 7 天**、导出可选"仅最近 1 小时"。

## 12. 迁移步骤（每步可停、每步可验）

| 步 | 内容 | 验收 |
|---|---|---|
| **M0** | 立 schema 与事件 sink；新代码走新通道，旧的**暂时并存** | 新事件能被导出；旧功能全部不变 |
| **M1** | `requestId` 贯通（扩展生成 → 服务端回显 → 双方落同一值） | 一次失败在两侧日志里能按 requestId 对上 |
| **M2** | `failure` 覆盖全部抛出点（尤其 imageDownloader） | 造一次下载失败 → 事件流里必有一条 failure |
| **M3** | 支持包一键导出（env / settings / events / server-tail / summary.md） | 弹窗一键拿到 zip；summary.md 能回答 Q1–Q6 |
| **M4** | 逐个下线旧出口：DOM 遥测 → console → 服务端三件套 → `/log/page` | 每下线一个，护栏红一次即回滚 |

## 13. 开源配套

支持包是**单文件 JSON**（§4.2），所以 issue 模板只需要：

1. 把 `dmb-support-*.json` 拖进 issue（或贴 `summary` 部分）；
2. 一句话复现步骤；
3. 期望与实际。

`docs/LOGGING.md` 需要写清：字段字典、开关默认值、**以及"默认日志不含原文"这句承诺**（用户才敢发）。
支持包内 `privacy` 字段自带声明（`containsOriginalText`），机器可校验。
