## 三、架构关键事实（新会话必读）

### 译图呈现与缓存
- 站点 `<img>` 的 src **永不改写**；译图画在常驻画框上（挂 body，站点重建图片 DOM 动不到它）。
- **z-index 比大小只在同一层叠上下文里成立**——数字大 ≠ 赢，先看挂哪（真踩过：按钮被困 #i1 的 z=1 锅里）。
- 画框 2147483000 < 按钮 2147483001 < （已删的阅读栏 3002）。新浮层按此序列往上排。
- 缓存只活内存；淘汰只在写入时发生（调小上限要立刻 trim，真踩过）。

### 调度 / 预取
- 优先级 P0（当前页，distance 0）> P1 > P2 > P3，按优先级 + 入队顺序排序。
- 预取链从 showpage JSON 的 `n` 字段链式爬；showkey 内联脚本提取；节流 250ms。
- `translateInBackground` 对 `isKeyBusy(key)` 直接 return（不重发）→ 快翻 = 自然接管在跑任务，完成时 `resolveTarget(key)` 贴图。
- 管线并发恒 1、不可抢占；单图正常区间 **2.3–7.3s**。
- 当前页自动翻译 = 执行器窗口下界 `Math.max(0, …)`；预载关 = `Math.max(1, …)`（现由 autoTranslateOnEnter 控制）。

### e-hentai 站点事实
- 页身份 = `${gid}-${page}`，**只从 `location.pathname` 派生**（`/s/{imgkey}/{gid}-{page}`）。
- 图址含逐请求签名 `keystamp=` → 任何含图址的缓存键必然永不命中（M0 教训）。
- 翻页走 `api.php?f=showpage` 软导航，零整页重载。
- 站点全局（gid/showkey/load_image/apply_json_state）`document_start` 全 undefined，`window load` 才挂上 → 主世界 hook 必须「晚挂」；prototype 级补丁（XHR/fetch）document_start 打就 100% 有效。
- 主世界的唯一必要性：下一页图址只在 showpage 回包里（带一次性签名，猜不出），只有主世界能在站点收到回包那一刻看到它。两世界传话只能 postMessage / documentElement 属性（DOM 属性是唯一共同可见区）。

### 诊断器设计铁律
- **判定里不许出现时间阈值**（QUIET_MS / settled 窗一律作废）：站点静默 ≠ 状态稳定。
- 优先用被测方自己声明的权威值（showpage 响应的 p+k 就是图身份），别自己轮询 DOM 找「稳定帧」。
- 采样/分段判定用**位置序列**（如 7→8→7 两段 = 两次访问），不用时间间隔。
- 信号拿不到判 inconclusive，不许空集通过、不许时间兜底。
- 探针 UI 不许打印假 success：先查 `chrome.runtime.lastError` 并确认副作用真的发生。
- 探针「0 数据」先分清「没采到」还是「采到了但为空」：content script 一注入必然自带刻痕事件，0 条 = 压根没注入。
- 一个阶段一支独立诊断器，旧冻结归档；结论先沉淀再推进。

### 推进纪律（用户定，优先级最高）
- **目的是完成项目要求，不是把现在的 bug 修好。** FAIL 先三分定性：①真机业务事实（动产品代码）②测量/工具误差（登记归档不修）③本项目本就要修的目标本身（按里程碑推进）。严禁因为诊断器报 FAIL 就回去改诊断器。

### UI 惯例
- popup 给 input 定宽必须带 `.panel` 前缀抬特异性，否则全局规则必赢（真踩过）。
- 给弹窗加东西默认一行收纳，别做全宽按钮。

# 附：v0.4.1（2026-10-04）—— 后台报错清零

承接上文 §四 遗留清单第 1 项。当前后台控制台已无任何报错（用户真机确认：重启不报、进画廊不报、翻译不报）。

## 一、根因：端口监听器的**注册层**会抛，回调内 try/catch 接不到

- 报错形态：`Error in event handler: Error: Extension context invalidated. at .../chunks/index2.js:8:30947`
- 归属确认：`chunks/index2.js` 只被 `background-chromium.js` 引用 → 报错在 **Service Worker**。
- **按列号精算**：30694 / 30947 都精确落在 `port.onDisconnect.addListener(...)` 这个**注册语句本身**。
- **机理**：上下文失效后，连 `port.onDisconnect` 的**属性访问**都会抛；抛出点在 `addListener(...)` 这一层，
  写在回调**内部**的 try/catch 接不到（回调压根没注册上）。
  `contentSessionLifecycle.ts` 早有一个回调内 try/catch（注释还专门写了防 invalidated），照样报错。
- **取证教训**：曾误判「偏移不变 = 旧代码残留」，实际是我改的代码编进了另一个 chunk，
  index2.js 两次构建内容一致。**偏移取证前必须先验证该文件这次是否真的变了。**

## 二、修法：共享守卫（可复用，非补丁）

`shared/extensionRuntime.ts` 新增两个导出：

- `guardExtensionListener(listener)` —— 回调层：只吞 invalidated，其余照抛
- `guardRegistration(register)` —— **注册层**：包在 `addListener(...)` 外面，返回 false 表示上下文已失效

接线：background 三处 `onConnect`（contentSessionLifecycle / extensionControlPort / offscreenBroker）
及其 port 监听器，内容脚本 `localPipelineClient.ts` 的 4 组端口监听器。测试 11 条。

- 坑：`const send = runtime.sendMessage; send(...)` 这种 detached 调用在 Chrome 会
  `Illegal invocation` —— 走仓库已有的 `sendRuntimeMessage`。

## 二、M4 预取：窗口边缘不推进（真根因）

- **现象**：预载计数停在 2/3 两分钟不动；翻页有时只能冷启动（"从读图开始"）。
- **根因**：链是**逐跳接龙**的（请求第 P 页必须持有 P 的 imgkey，而 imgkey 只在前一页 JSON 里），
  而 `onPageArrived` 里「到达页的数据已在手就**原地返回**」—— 新窗口的**边缘页**是新的，
  于是**每翻一页窗口尾部就永久缺一页数据**。
- **修法**：新增 `advanceToWindowEdge()`：到达时从当前页沿**已在手**的 JSON 逐跳找缺口，
  遇到第一个未请求页就派发（imgkey 就在前一页 JSON 里），随后停；它的 JSON 回流后由 ingest 接着爬。
  只读内存档 + 只发缺失那一页，**零定时器、零多余请求**。测试 7 条。
- **失败补救**：`showpageClient` 加 15s 硬超时（挂死也算失败）与 `onDispatchFailed`；
  链 `notifyDispatchFailed` 把该页从去重集放出（否则它永不再被请求、后段整条链断）并**自动补发一次**；
  出窗的失败不追、成功后的迟到失败不计。

## 三、被裁掉的"诊断装置"（记录判断，避免重复踩）

定位过程中曾加过：缺口原因分类（数据缺/翻译失败/停滞）、末页截断分母、`advancing` 标志、
`requested` 提前计数。**这些都不是需求**（需求只有"显示数量"），且这类观测装置要在
"活还在路上"的一瞬间判断状态，**天然有竞态**（真机表现：有概率闪一下"数据缺"）。
用奥卡姆剃刀整套撤掉（`2e9136a`，净删 136 行），全量事实回到遥测
`documentElement.dataset.m5Chain`（chain/dispatch/executor 三份快照），需要时再读。

**纪律**：为一个 bug 加的观测代码，bug 修完后要主动清算 —— 删掉它会不会影响需求？
不会就删，别让诊断代码变成新的 bug 源。

## 一、OCR 改走 server 的 manga-ocr（不再用浏览器 ONNX OCR）

- 新增 `serverMangaOcrProvider`：整行 crop → data URL → `POST {base}/ocr` → 按 id 映射回区域；
  `requiresModelRuntime:false`（不建任何浏览器 ONNX 会话）。`settings.ocrEngine` 默认改为
  `manga_ocr_server`；本地 PaddleOCR provider 代码保留为备选。
- **失败显式报错，绝不静默回退本地 ONNX**（服务不可达 / 非 200 / 少返回一行都失败）——
  静默换引擎会把"服务没开"伪装成"翻译质量变差"。
- orchestrator 的 OCR 运行时预热按引擎门控：原来那一站**无条件加载 PaddleOCR 权重（~76MB）**，
  现在走服务端就一个会话都不建。
- 坑：`ocrServerBaseUrl` 只能从**回环地址**派生。默认 LLM 是云端（deepseek），
  按"来源"派生会把 OCR 请求发到 `https://api.deepseek.com/ocr`。已配测试钉死。

### 顺带修掉的真缺陷：OCR 置信度口径

真机实测 manga-ocr 的 generation_config 是 **`num_beams=4 / length_penalty=2.0`**（beam search）：

- `generate().scores` 是「batch × beams」条分布，**无法按行归属** —— 同一张图单独跑 0.2144、
  混进批量变 0.0（8 个候选里都找不到真值）。
- 原实现的"概率几何平均"还**长度敏感**：完全正确的 16 字文本只给 0.0257，而调用方以 0.3 判"可疑"
  → 每一行白吃一个可疑信号。
- 改用 HF `sequences_scores`（返回序列自身分数）反推平均每 token 负对数似然：
  `mean_logprob = score * len ** (penalty - 1)` → `conf = 1/(1+mean_nll)`。
  长度无关、批量与单行一致（真机 cc-100 样例 0.399，文本正确）。

## 二、ollama 与模型控制拆成独立服务（`server/ollama_server.py`，11437）

原先"模型加载/卸载/状态"由 dmb_server（11436）提供 → 管模型被绑死在 OCR/翻译服务上，
dmb_server 一关就管不了模型。现在三个进程互不依赖：

| 进程 | 端口 | 职责 |
|---|---|---|
| `app.py` | 11436 | manga-ocr（`/ocr`）+ Sakura 规范化翻译（`/v1/chat/completions`） |
| `ollama_server.py` | 11437 | ollama 引擎启停 + 模型状态/加载/卸载 |
| ollama 引擎 | 11434 | 推理（由 11437 拉起） |

- `app.py` **删掉全部 `/model/*` 路由**与启动清显存；扩展的模型 UI 与 ollama 探活改指 11437。
- Native Messaging 的 `target=ollama` 改指这个服务；关停走它自己的优雅通道 `POST /shutdown`。
- 新脚本 `scripts/start_ollama.cmd` / `stop_ollama.cmd`；面板拆两张（模型面板归 ollama 服务）。

### 关停/卸载的强制语义（不能"回弹"）

- **关闭 ollama**：① 先 `keep_alive:0` 卸载全部驻留模型（强制：正在跑的推理也停）→
  ② 再结束整棵进程树（`ollama app.exe` / `ollama.exe` / 模型 runner）→ ③ 确认端口关闭。
  **顺序不能反**：引擎先死就再也发不出卸载请求，显存只能被动释放、状态残留 → 就是"回弹"。
- **卸载单个模型**：温和请求 + 1s 宽限期确认，仍在驻留就直接结束 runner —— 不被"进程正在跑"卡住。

## 三、删掉整页"配对"机制 + 停写 OCR 归档（`16b5d5f`，净删 222 行）

`pages.py` 想把「同页 OCR + 同页翻译」合成一条 `kind=page` 记录（v1 的教训是 FIFO 猜测会错配，
所以 v2 只认显式 pageKey）。**实测它在真机从未生效**：真机日志 10-03（211 条）+ 10-04（260 条）
全部是 `pairing: none(no pageKey)`，`kind=page` 一条都没有 —— 因为配对要两个请求都带 pageKey，
而扩展的翻译请求从构造起就不带（body 由 text-translation 包产出），OCR 以前又是浏览器本地跑的。

现状口径：**翻译侧照旧落一条** `image.jsonl`（`translate_list` + 分阶段耗时，已无 pageKey/pairing/kind），
**OCR 侧不再落归档**（没配对的纯噪音）。`pageKey` 标识本身保留 —— 它是扩展的页身份与译图缓存键。

## 四、UI 三处（都是用户真机反馈驱动的）

1. **两个服务开关不再互相阻塞**：`busy` 原是 `ServiceKind | null`，渲染时被压成布尔喂给两个开关
